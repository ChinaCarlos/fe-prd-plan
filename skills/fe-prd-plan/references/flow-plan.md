# 第二步：任务拆分 + 生成 plan.md

输入 = `flow-fetch.md` 归档的 md（或用户直接粘贴的需求文本）。本流程不做完整度评估、不做需求分级、不建 hub/registry/meta.yaml/change 目录——只做「拆任务 → 出计划 → 对话确认」这一段最短路径。

## ① task 拆分

每个 task = **最小可独立验证单元**：能单独判定完成，不与其它 task 耦合到无法单独验收。粒度以「可独立验证」为唯一标准，不是文件数或工时估算。一个需求可能拆成多个 task，一个 task 也可能覆盖多个小需求。

## ② 分型判定（写死规则，不当场感觉）

| 判定条件 | type |
|---|---|
| 业务逻辑 / 数据处理 / 接口 / 状态管理 | `tdd` |
| 纯布局 / 动效 / 平台 UI 适配 | `ui-verify` |
| 纯文档 / 流程文本（无可测运行时行为） | `docs` |
| 无测试基建、仅能验证构建产物 | `build-verify` |

**可测逻辑混进 `ui-verify` task = 拆分失败**，必须拆出独立 `tdd` task，防止"整个需求都是 UI"的合理化逃逸。

`ui-verify` task 必须声明验证方式与对照来源（截图/实机对照 + 来源文档章节或设计稿）；非 UI 需求不应出现 `ui-verify` task。

## ③ 生成 plan.md

按 `skeletons/plan.md.skeleton` 骨架写：
- 有归档来源：`docs/prd/<归档目录名>/plan.md`
- 无归档来源（用户直接粘贴需求文本）：落到用户指定目录或当前工作目录下的 `plan.md`

## ④ 自审

- placeholder 扫描：骨架占位符（`<...>`）是否已全部替换
- 需求覆盖度：归档文档/粘贴文本中的每条需求是否都能在任务表中找到对应 task，无遗漏
- 分型一致性：同一份 plan 内不应出现"同类逻辑一半标 tdd 一半标 ui-verify"的不一致

## ⑤ 对话渲染纪律（强制）

任务总览表必须**完整渲染进对话**，不能只写文件不展示——文件是存档，对话是确认界面。

## ⑥ 确认即完成

等待用户「确认 / 继续 / 按此计划开发」后，本 Skill 完成职责。后续实现按目标项目既有开发流程进行；本 Skill 不派发 SubAgent、不写代码、不引入 `dev_mode`/`meta.yaml` 概念。
